# Public Review Path

This is the recommended path for reviewers who need to understand the portfolio quickly while preserving the claim boundary.

## 1. `README.md`

- **Why read it:** It gives the top-level positioning, status, contribution boundary, and reviewer orientation.
- **What it proves:** The repository is intentionally framed as an Onyx-based AI security-readiness portfolio with explicit NO-GO / PENDING / NOT CLAIMED language.
- **What it does not prove:** It does not prove production readiness, enterprise readiness, external validation, compliance certification, full live staging, or live enforcement.

## 2. `PORTFOLIO_CASE_STUDY.md`

- **Why read it:** It summarizes the portfolio story for a professional reviewer.
- **What it proves:** The work is organized as a case study around evidence discipline, threat-model thinking, demo attacks, and launch-gate boundaries.
- **What it does not prove:** It does not prove the system was deployed, externally audited, certified, or accepted for production use.

## 3. `CLAIM_BOUNDARY.md`

- **Why read it:** It is the safest place to verify allowed, forbidden, and status-boundary wording.
- **What it proves:** The repository has explicit public-claim controls.
- **What it does not prove:** It does not prove every future reviewer conversation or external post will preserve the boundary without manual review.

## 4. `portfolio/README.md`

- **Why read it:** It provides the concise reviewer package for agencies, clients, partners, and employers.
- **What it proves:** Reviewers can navigate the portfolio package without reading the entire repository first.
- **What it does not prove:** It does not prove runtime security controls are active in live application paths.

## 5. `portfolio/evidence_index.md`

- **Why read it:** It maps reviewer questions to repository evidence and limitations.
- **What it proves:** Evidence is indexed with proof statements and non-proof statements.
- **What it does not prove:** It does not convert documentation, isolated helpers, or CI checks into production controls.

## 6. `demo_attacks/README.md`

- **Why read it:** It explains the synthetic demo attack runner and expected reviewer-safe evaluation path.
- **What it proves:** The repository includes synthetic scenarios for local reviewer evaluation.
- **What it does not prove:** It does not prove live adversarial testing, live blocking, live filtering, or full RAG production defense.

## 7. `docs/security/evidence/final_portfolio_package/README.md`

- **Why read it:** It bundles the final evidence package for portfolio review.
- **What it proves:** The project has a final reviewer-facing evidence package with readiness score, checklist, and gaps.
- **What it does not prove:** It does not prove production-system readiness or compliance certification.

## 8. `portfolio/release_prep/README.md`

- **Why read it:** It shows release-prep checklists for screenshots, video, notes, sanitization, and final review.
- **What it proves:** Public-sharing preparation is documented before distribution.
- **What it does not prove:** It does not create screenshots, video evidence, deployment evidence, or external validation.

## 9. `docs/security/known_limitations.md`

- **Why read it:** It lists the remaining limitations reviewers should consider before trusting claims.
- **What it proves:** The portfolio keeps limitations visible instead of hiding unresolved gaps.
- **What it does not prove:** It does not remediate the limitations or authorize production use.
